# 環境構築とデモの起動

[プロジェクト紹介](../../README.md) / [ドキュメント一覧](../README.md)

## 必要なもの

- macOS + Docker Desktop（Apple Siliconで動作確認）
- [uv](https://docs.astral.sh/uv/)とPython 3.12以降
- Node.js 20以降とnpm（フロントエンドのビルド）
- OrcaRouter APIキー（実際のAI推論を試す場合）

シミュレータはネットワーク名前空間を作るため、Dockerの`privileged`コンテナで動作します。
APIキーがなくても固定手順による調査を試せます。録画応答を使った構成図解析は実推論と区別して表示します。

## 起動する

初回はリポジトリを取得し、そのディレクトリへ移動します。

```bash
git clone https://github.com/Shibata-1273352/AIHack2026-09.git
cd AIHack2026-09
```

OrcaRouterを使う場合は、初回のみ設定例をコピーし、`backend/.env`を編集します。
設定済みの`.env`は上書きしないでください。

```bash
cp backend/.env.example backend/.env
```

`ORCAROUTER_API_KEY`に自分のAPIキーを設定してから起動します。`.env`はGitの管理対象外です。

```bash
./demo.sh
```

初回はコンテナのビルドと依存関係の導入に数分かかります。
起動スクリプトはシミュレータを作り直すため、進行中の実演を再開したい場合は、まず`./demo.sh status`で状態を確認してください。

起動後は、ターミナルに表示される**トークン付きURL**を開きます。

| 画面 | パス | 用途 |
| --- | --- | --- |
| Macコンソール | `/console` | 構成図の読込・申告・調査・承認・復旧確認 |
| iPad承認画面 | `/approve` | 差分と検証結果を見て承認・却下 |
| デモ運転席 | `/ops` | 環境のリセット・障害の再現 |

バックエンドは8000番、シミュレータの制御APIはホストの`127.0.0.1:9000`を使用します。
iPadはMacと同じWi-Fiに接続し、表示されたMacのIPアドレスを含むURLを開きます。

`demo.sh`は起動ごとに操作トークンを生成します。承認・障害注入・リセットにはこのトークンが必要です。
トークン付きURLは公開資料やスクリーンショットに含めないでください。
バックエンドを直接起動し、`APPROVAL_TOKEN`を設定しない場合は認証なしの開発モードになります。

## デモを試す

1. コンソール右上の「デモをリセット」で正常状態に戻します。
2. 「デモPDFで試す」、またはPDFの選択・ドロップで構成図を解析します。「登録構成と一致」を確認します。
3. 「複合障害を再現」で、主回線停止と予備経路の通信ルールの誤設定を再現します。
4. 業務不通を確認して「申告して調査を開始」を選びます。
5. 調査と事前検証の結果を確認し、コンソールまたはiPadで変更を承認します。
6. 業務復旧と残存課題を確認します。再実演するときはリセットします。

構成図を選択しない場合は組み込み構成図を使用します。
PDFは暗号化されていない1〜3ページ・10MB以下に対応し、実推論時には画像と抽出テキストをOrcaRouterへ送信します。
デモPDFは[こちら](../../backend/assets/netwalker-demo-topology.pdf)から取得できます。

解析失敗や登録構成との不一致があるPDFでは調査を開始できません。
処理中はリセットできませんが、承認待ち・終了後にはリセットできます。
過去の案件・証拠は保持し、旧案件への承認は拒否します。同じ画面内では選択済みPDFの解析結果を再利用できます。

発表の説明と時間配分は[デモ台本](../demo-script.md)を参照してください。

## 実行モードと設定

| 設定 | 値と意味 |
| --- | --- |
| `ORCAROUTER_API_KEY` | APIキー。互換名は`ORCA_API_KEY`。ルートまたは`backend/.env`から読み込み |
| `NW_AGENT_MODE` | `auto`：キーがあればLLM、なければ固定手順。`llm` / `scripted`も指定可能 |
| `NW_ROUTE_MODE` | `live`：実呼出。`record`：実呼出と録画保存。`mock`：録画応答の再生 |
| `APPROVAL_TOKEN` | 操作トークン。`demo.sh`へ環境変数で渡せばその値を使用し、なければ生成 |

`live`でのAPI失敗時には、利用できる録画応答があれば再生へ切り替え、その事実を表示します。
録画応答がない場合やガードレールによる遮断は、常にデモが続くことを保証しません。画面の状態と理由を確認してください。
モデル候補や費用管理の設計は[アーキテクチャ](../architecture.md)、比較条件は[評価ガイド](../evaluation/README.md)を参照してください。

## 停止・状態確認・困ったとき

```bash
./demo.sh status
./demo.sh stop
```

| 症状 | 確認すること |
| --- | --- |
| 起動しない | Docker Desktopの起動、8000/9000番の使用状況、`backend.out.log`と`docker logs nwsim` |
| 承認やリセットが403になる | 今回の起動時に表示されたトークン付きURLから開き直す |
| リセットが409になる | 解析・調査・適用処理の終了を待つ |
| 設定変更が反映されない | デモを終了して`./demo.sh stop`、続いて`./demo.sh`で再起動 |
| ソースを変更しても画面が変わらない | [開発ガイド](../development/README.md)の手順でフロントを再ビルド |
| 再起動後に案件の状態が合わない | 外部状態との自動照合は未実装。処理状況を確認し、デモをリセットして再実演 |
