## 誰も嘘をついていないのに、復旧しない

拠点の担当者が「受注画面が開かない」と言う。ネットワークの知識はない。
情シスに電話すると「回線は生きています」。回線事業者に聞くと「弊社の設備は正常です」。

**たらい回しの間、業務は止まったまま。**

しかもこの状況、**誰も嘘をついていない**ことがあります。たとえば主回線が切れて
冗長化制御が予備回線へ自動で切り替わり、その予備回線側に別の設定ミスがある場合。
切替は正常に機能しているので「回線は生きている」は本当だし、
事業者設備も正常なので「弊社は正常」も本当です。

NetWalker は、この最初の一言を入口に、AIエージェントが実際のネットワークを調査し、
原因を証拠付きで特定し、修正を複製環境で検証し、**人間の承認を得てから**適用して、
業務が戻ったことを確認するところまでを一本の流れで行います。

## 作ったもの

![構成図](/images/netwalker-topology.png)
*デモ環境の構成。Linux の network namespace で5機器を組み、nginx が本物の TLS で
待ち受け、nftables が実際にパケットを落とす。*

デモでは、わざと2つの障害を同時に起こします。

- **障害A**: 主回線のリンク断（冗長化制御が予備回線へ自動切替する）
- **障害B**: 予備回線のルータに、業務通信だけを落とす誤った通信ルール

Aだけなら予備回線に切り替わって業務は続く。Bだけなら主回線を使っているので気づかない。
**両方同時に起きると業務が止まる**。この「単一原因では説明がつかない」状況が、
実際にいちばん困るところです。

### 「絵」ではなく本物のネットワーク

ここは強調したい点です。シミュレータは画面上の演出ではありません。

- Linux の **network namespace を10個**（対象環境5 + 検証用複製5）
- nginx が**本物の TLS** で受注サービスを提供
- **nftables が実際にパケットを落とす**
- telnet は待ち受けているが、ポリシーで遮断されている

エージェントが実行する `curl` / `ip` / `nft` の出力が、そのまま画面の証拠になります。
画面下のバッジには名前空間の数と主回線の状態が出ていて、**デモ中に実際に変化します**。

## デモの流れ

### 1. 障害を入れる — その瞬間、機器が自力で直る

障害を注入すると、まずこれが出ます。

> **機器が自分で切り替えました（AIではありません）**
> `10:14:22` 主回線の切断を検知（1秒ごとに監視・3回連続で確定）
> `10:14:25` 予備回線へ自動切替 — 約3秒で完了
> ここまでは装置の機能です。**それでも業務は止まったまま。ここからが NetWalker の仕事です。**

これは冗長化制御デーモンが実際に書いた履歴です。AIの手柄を水増ししないための表示
ですが、結果として**物語の起点**になりました。
「装置は正しく動いた。それでも人が困っている」という、この題材そのものの説明になります。

### 2. 申告 → 調査

申告ボタンを押すと調査が始まります。接続情報も許可範囲も導入時に登録済みなので、
**再入力はありません**。

そして調査ログが**積み上がっていきます**。

```
10:14:31 業務通信を実測し、申告のとおりか確かめます                証拠 1件
10:14:34 構成図をAIが読み取り、登録済みの機器一覧と照合します       証拠 1件
10:14:49 AIの判断1：通信できるか経路を試験します                   証拠 1件
         OrcaRouter が balanced 戦略で openai/gpt-oss-120b を選択（fallback 0）
10:15:01 AIの判断2：拠点ルータの自動切替の状態を確認します          証拠 1件
         OrcaRouter が balanced 戦略で openai/gpt-oss-120b を選択（fallback 0）
10:15:13 AIの判断3：予備回線ルータの通信ルールを確認します          証拠 1件
         OrcaRouter が balanced 戦略で openai/gpt-oss-120b を選択（fallback 0）
10:15:25 AIの判断4：修正案をまとめます
```

見どころは2つあります。

**手順が固定ではない**こと。上のログは「業務通信を実測 → 構成図を照合 →
拠点ルータ → 主回線の断線 → 予備回線を層別に確認 → 原因発見」と進んでいますが、
障害の種類が変われば経路も変わります。手順書を読み上げているのではなく、
**観測した結果に応じて次の手が変わっている**のが読めます。

もう1つは各行の青い文字。**その判断にどのモデルがなぜ選ばれたか**です。
判断ごとに選び直されている様子がそのまま見えます。

### 3. 本番に触る前に、複製環境で試す

ここが個人的にいちばん手応えのあった部分です。

> **本番に触る前に、そっくりな複製環境で試しました**
> ① 複製をつくった — 本番と同じ構成であることを確認
> ② 変更する前 — 業務通信 NG ／ 禁止通信 遮断されている
> ③ 変更したあと — 業務通信 OK ／ 禁止通信 遮断されたまま
> ④ 判定 合格 → だから本番に出せます

複製は「だいたい同じ」ではありません。リンク状態・経路・ルールセット・待受ポート、
さらに**業務テストと禁止通信テストの結果まで**一致することを機械で確認してから
試しています。一致しなければ承認待ちへ進みません。

### 4. 最後の判断は人に

承認画面には、AIの要約ではなく**実際に流す変更の1行そのもの**と、
複製環境での変更前後の実測結果が出ます。ボタンの下には
「**承認した1件以外は、何も変更されません**」。

承認は計画のハッシュに紐付くので、「人間が特定のハッシュの計画を承認した」ことが
記録に残ります。版・ハッシュ・期限・承認者はすべてサーバ側で照合し、
古い画面からの承認や二重承認は拒否します。

**却下しても行き止まりになりません。** 「ネットワークには何も変更していません」を
明示したうえで、引き継ぎレコードを起票し、「もう一度調べ直す」「担当者に引き継ぐ」
の出口を出します。調べ直しは障害を入れ直さずに続けられます。

### 5. 復旧、ただし「全部直った」とは言わない

適用後、利用者と同じ通信で3回連続の成功と、止めるべき通信が止まったままであることを
確認します。そのうえで、

> 業務は復旧しました。ただし**主回線の断線は物理の問題なので直していません**。
> 残存課題として、回線事業者の保守窓口へ引き継ぎます。

で終わります。全部直ったと言わないことが、この作品の中身そのものだと思っています。

## 実測してみて分かったこと

### 「安いモデル＝良いモデル」ではなかった

候補モデルを**実タスク**に通す検証スクリプトを書きました。判断1ステップ
（構造化出力）と構成図読取（vision + 構造化出力）を同じ入力で回し、
合否・実請求額・レイテンシを測ります。15モデル × 2タスク。

結果が予想と違いました。

- **単価が最安のモデルは、構造化出力に不合格**。しかも 400 で落ちるのではなく
  **200 を返してスキーマに適合しない**。つまり課金はされるのに採用できない
- **それまでの第一候補は、構成図の接続を5本中4本しか読めていなかった**。
  「動いている」と思っていたものが、静かに1本取りこぼしていた
- **無料枠はどれも完走しない**（レート制限か課金エラー）。
  「実質0円で復旧まで到達」という気持ちのいい一文を書きたかったのですが、
  実測で言えないので書きません
- いちばん安く合格したのは**製品の Named Router に選択を委ねる**方式で、
  判断と構成図読取で**別のモデル**へ解決していました。
  それまでの第一候補と比べて構成図読取の実費は 1/33 になり、しかも読み落としがない

単価表を眺めているだけでは、どれも分かりませんでした。
**合格したモデルだけを候補列と画面の選択肢に載せる**運用にしています。

### 費用は「推定」をやめて「実請求額」にした

最初は「ルータは原価を返さない」と思い込んで、単価表 × トークン数で推定していました。
ところが応答ヘッダの request id を費用照会APIに投げると、
**確定請求額（`total_cost`）が返る**と分かりました。

推定で「安いです」と言うのと、請求額で言うのとでは説得力が違うので、
**表示と評価はすべて実請求額**に切り替えました。

ただし呼出の**前**には実費が分からないので、予算の事前判定は単価表のまま残しています。
ここで穴が1つありました。**Named Router や無料枠は単価が公開されません**。
単価不明を「0円」として扱うと、**費用上限が事実上無限になります**。
保守的な上振れ単価で見積る経路を足して塞ぎました。

## 画面を作り直した話

決勝は**4分発表 + 3分質疑**で、審査員に非エンジニアが含まれます。つまり
**コンソール画面そのものがプレゼン**で、読み解きに時間がかかる画面は
実装の良し悪しと関係なく減点になります。ここが弱かったので作り直しました。

### 用語は「消す」のではなく「二層にする」

`AI判断3: observe_node` とか `SERVICE_RESTORED: 業務通信は回復` とか、
生の設定ルールがそのまま見出しに出ていました。かといって技術用語を全部消すと、
技術がある人には逆に薄く見えます。

そこで**表示層と技術層を分けました**。バックエンド側はこう書くだけです。

```python
publish_step(incident_id,
             "予備回線ルータの通信ルールを確認します",    # 画面に出る平易層
             tech_title="observe_node r2 [link, nft]",   # 技術詳細モーダル側
             tech_detail="...")
```

状態遷移も、それまで「注記がそのまま画面見出しになる」構造だったのを、
注記は技術層へ・見出しは状態ラベル由来に変えるだけで、**18箇所が一括で平易化**
されました。文字列を1つずつ直すのではなく、
**どこで文字列が画面に漏れているか**を直すほうが早い、というのが学びです。

### 調査ログを「上書き」から「積み上げ」に変えた

いちばん効いたのはこれでした。「調査の進行」カードが**最新の1件で上書き**されていて、
AIが一生懸命調べている過程が画面に残っていませんでした。
全ステップはもともと配信されていて、**描いていなかっただけ**でした。

積み上げ表示に変えるだけで、推論の流れがそのまま読めるようになりました。
自律性の証拠として、これ以上のものは用意できませんでした。

## 実装の途中で見つけたバグ

いい話ばかり書いても仕方ないので、作業中に見つけた自分のバグを3つ書きます。

### 1. 防御が発動するとアプリが落ちる

ゲートウェイのガードレールが遮断すると 400 が返ります。ところが実装は
「400 は再試行不可なので即座に例外送出」になっていました。つまり
**ガードレールが正しく仕事をした瞬間に、調査そのものが異常終了**していました。

防御の発動がアプリの障害に見えるのは設計として誤りなので、
ガードレール起因の 400 を判別して専用例外にし、案件は安全停止させ、画面には
「**ゲートウェイが送信内容を遮断しました**（AIには渡っていません）」と、
**設計どおりの防御動作**として出すようにしました。

### 2. 構成図の読取が表記ゆれで壊れる

構成図PDFを作り直したあと、実キーで検証したら照合に失敗しました。原因は、
1機器が3行（機器ID・和名・IPアドレス）で描かれていると、読取結果も
`"client\n業務端末\n10.0.1.10/24"` という**複数行ラベル**で返ってくることでした。
登録機器表との突き合わせは完全一致だったので、そこで落ちていました。

行単位でも照合し、**一意に1台へ収束するときだけ**対応付けるように直しました
（複数台に当たる曖昧なラベルは確認待ちのまま）。
再実行したら今度はモデルがきれいなラベルを返したので、
**そのまま気づかず本番を迎えていた可能性**があります。実キーで確かめてよかった。

### 3. 費用確定処理が承認をブロックする

実請求額を案件終了時に引く処理を足したのですが、それを調査スレッドの中で
同期実行していました。結果、**承認待ちに入った直後の承認が 409 で弾かれる**ように
なっていました（処理中は承認を受け付けない仕組みのため）。

人の操作なら数秒あくので気づきにくいのですが、自動テストは即座に承認するので
そこで露見しました。費用照会は読取と記録だけの後処理なので、別スレッドへ
切り離して解決しました。

## 正直に書いておく限界

- 実機・マルチベンダー機器は対象外。netns + nftables の Linux 等価環境
- 冗長化制御は自作の簡易デーモン（BGP/VRRP の実装ではない）
- ローカルLLM は未接続。接続していないものを接続済みのようには見せていない
- **利用者認証が無い**（変更系APIの共有トークンのみ）。承認者名は自己申告
- **記録はあるが通知が無い**。異常を人へ push する経路は未実装
- ゲートウェイのファイアウォールは**シャドーモード（監視のみ）**。
  実際に操作を止めているのはアプリ側のホワイトリストと承認ゲート
- プロセス再起動後の状態照合は未実装／CI 未導入（テストはローカル38件）

## おわりに

作りながらいちばん考えたのは、**「AIが直しました」と言わせないこと**でした。

装置が自力で切り替えたところは装置の手柄として書く。
複製環境で確かめてから本番に出す。最後の判断は人に渡す。
直せなかったものは残存課題として引き継ぐ。

派手さはありませんが、実際に業務ネットワークへ入れるとしたら、
この順番でしか信用されないと思っています。
